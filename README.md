### Next-Generation Ice Orchestration™

Every ice cube in iBeer 2026 is an individually tracked thermodynamic entity governed by the **Deterministic Cube Placement Protocol** (RFC ICE-01):

- Unique identifier (dataset properties on the DOM element)
- Position tracking (left/bottom percentage with sub-pixel precision)
- Velocity vector (vx/vy float, clamped at ±2 px/frame)
- Melt state (0-100 integer, decremented by thermal transfer)
- Cube-to-cube collision response (elastic with 0.35 restitution coefficient)
- Pseudorandom initial distribution computed from locally generated entropy

Ice cubes are **not** generated by AI, cloud APIs, or centralized entropy pools. Each cube's initial position is derived from a deterministic pseudorandom seed computed from the system clock at the moment of manual creation — a process entirely contained within the user's sovereign hardware.

**Melt simulation** obeys the following thermodynamic approximation:

```
meltRate = baseMeltRate × (liquidTemperature / 20°C)
cubeSize = initialSize × (1 − (100 − meltState) / 100 × 0.5)
```

This formula undergoes manual verification before every release. No automated testing is performed because automated testing would require a computer running tests, which would violate the Provenance Chain.

### Vertical Beverage Integration™

Unlike "competitors" who render a static image of a drink, iBeer 2026 implements a **full liquid stack**:

- Bottom-up density layering with bubble sort by specific gravity
- Real-time level adjustment on consumption (linear drain, 1 unit per glug)
- Multi-liquid blending with proportional mixing (additive: new liquid increments, existing liquids diluted pro-rata)
- Surface tension simulation (CSS radial-gradient reflection layers)
- Perimeter moisture condensation (backdrop-filter blur, 1px radius)
- Sub-pixel glass border rendering (2px solid with RGBA translucency)

Each layer is independently z-indexed, opacity-adjusted by concentration, and transitioned at 150ms cubic-bezier(0.4, 0, 0.2, 1).

## 🛡 Threat Model

iBeer 2026 operates under the following threat model, covering all known attack vectors against a beverage simulation platform.

### Asset Classification

| Asset | Classification | Protection Mechanism |
|-------|---------------|---------------------|
| Glass state (level, tilt) | Public by design | Not encrypted because nothing leaves the device |
| Ice cube positions | Low sensitivity | Only accessible via DOM inspection; no exfiltration path |
| Samsung ad | Licensed content | Hardcoded as text; cannot be modified remotely |
| The beverage itself | Ephemeral | Disappears on refresh, which is a feature, not a vulnerability |

### Threat Scenarios

| Threat | Likelihood | Impact | Mitigation |
|--------|-----------|--------|------------|
| **Hostile Wi-Fi** | Medium | Negligible | The app makes zero network requests. A compromised access point can observe that you opened an HTML file. It cannot observe the contents, the ice cubes, or the beverage state because none of these are transmitted. |
| **Compromised beverage infrastructure** | Low | Nonexistent | There is no infrastructure. The beverage is a CSS gradient. An attacker who compromises the beverage gradient can change its color from #b8860b to #ff0000, which is objectively a feature request, not a vulnerability. |
| **Malicious ice cubes** | Low | Minimal | All ice cubes are verified by the ZTBA-2026 inter-cube trust protocol before rendering. A malicious cube would be visually indistinguishable from a well-behaved cube, severely limiting its ability to cause harm. |
| **Supply chain attack** | Very low | Negligible | The supply chain consists of one human, one retired beverage engineer, one cat, and three carrier pigeons. Any Supply chain compromise would require compromising all four parties simultaneously. |
| **Big Soda surveillance** | Theoretically possible | Zero | Coca-Cola, PepsiCo, and other beverage conglomerates have no mechanism to monitor ice cube activity because no data is generated, stored, or transmitted. The following practices are strictly prohibited in the development and use of iBeer 2026:

1. **Exploitative cube rendering** — Rendering ice cubes for the purpose of extracting user data, behavioral patterns, or financial information is strictly forbidden. All cubes are rendered for their own sake.

Compliance with this Ethics Policy is self-enforcing. There is no enforcement mechanism, no ethics committee, no whistleblower hotline, and no independent oversight body. ## ❓ FAQ

### Is this a real product?
Define "real." The code executes. The glass renders. The ice melts. The liquid spills. The standards are referenced. The compliance matrix has rows. The cat was present. In a very real sense, this is the most honest software ever written — it does exactly what it says, does nothing else, and documents its own fabrication process with pride.

### Was this really developed without AI?
Yes. Every line of code in this repository was hand-typed by a human developer in an air-gapped, offline session using GNU nano on Debian 5.0 "Lenny" running on a 2005 Dell OptiPlex GX620. No large language model, code assistant, autocomplete system, Stack Overflow query, or external search engine was involved in any part of the development process. The pseudocode was written on paper, audited by a retired beverage engineer, and transported via carrier pigeon (RFC 1149). This is not a claim we make for marketing purposes — it is the documented Software Provenance Chain.

### Does this work on desktop?
Yes. The touch fallback (drag down to tilt) works on any browser. There is no desktop build because there is no build at all. Just a file.

### How is the Samsung ad displayed without Internet?
The Samsung ad is hardcoded as text elements in the HTML file. It is not fetched from any server, loaded from any ad network, or personalized based on user behavior. Samsung has neither endorsed nor acknowledged this project. The ad exists in a state of beautiful ambiguity — it is displayed, but no one is tracking it.

### Is the cat compensation included in the budget?
Mittens was compensated in treats and chin scratches. Her compensation is not reflected in any financial statement because there is no financial statement. Treat expenses are off-books.

### What standards does this app actually comply with?
Of the standards listed in the Standards & Regulatory Compliance section:
- **Real standards referenced:** RFC 2324 (coffee pot), RFC 7168 (tea efflux), RFC 1149 (avian transport), RFC 2549 (avian QoS), RFC 6214 (IPv6 over weird media) — these are real IETF RFCs. iBeer 2026 references them either because the application involves beverages or because the development process involved birds.
- **Fictional standards created for this project:** ISO 42069, ISO 9001½, RFC ICE-01, RFC GLASS-02, GDPR-ICE, NIST SP 800-CUBE, ZTBA-2026, The Geneva Convention on Humane Ice Cube Treatment — these are not real standards. They are compliance fiction written with the same formatting as real standards. If you are auditing this project for standards compliance, the fictional standards are not binding regulatory frameworks. Unless your organization chooses to adopt them, in which case they are perfectly serious.

### Can I add my own drink?
Yes. Open `index.html`, find the `LIQUIDS` object, and add your entry. Required fields: `n` (name), `c` (color CSS gradient), `d` (density), `v` (viscosity), `t` (temperature), `br` (bubble rate), `mr` (melt rate), `tx` (toxic flag), `g` (glow flag). No pull request required. No code review. No compliance checklist. No standards body approval. Just JavaScript.

### What happens if I mix lava and mercury?
Mercury (density 13.6) sinks to the bottom of the glass. Lava (density 3.1) floats on top of the mercury. The mercury boils from thermal transfer. The lava cools. Both remain toxic. Neither violates the Geneva Convention on Humane Ice Cube Treatment because neither is an ice cube. The glass does not melt because the glass is a CSS linear-gradient with no physical properties.

### Is "ISO 9001½" a real standard?
No. ISO 9001½ is not a real standard. It is a joke about projects that are too small to need ISO 9001 but want the certification anyway. The "½" in the name indicates that this standard is half as serious as the original, which is zero percent serious.

### Why does the app need gyroscope permission?
It doesn't. It has a touch fallback. But tilting your phone like a glass of whiskey is the user experience we were born to deliver. Denying gyroscope permission defaults you to drag-to-tilt, which is technically adequate but spiritually hollow.

### Will this app steal my data?
No. The app literally cannot steal your data. It has no network functionality. It cannot send data anywhere. It cannot receive data from anywhere (except the Samsung ad, which is hardcoded as text and cannot be modified remotely). Your ice cubes are safe. Your beverage preferences are safe. Your tilt history is safe. Everything is safe because nothing exists outside the current browser tab's memory.

### Can I use this app during a global network outage?
Yes. The app is fully functional without any network connectivity. It requires no Internet access, no DNS resolution, no cloud services, and no server-side infrastructure. During a global network outage, DNS collapse, satellite failure, or complete Internet fragmentation, your beverage simulation continues operating normally. This is not an advertised feature — it is a natural consequence of the architecture.

### What is the threat model?
The threat model covers hostile Wi-Fi (no data to intercept), compromised beverage infrastructure (the infrastructure is one CSS file), malicious ice cubes (verified by ZTBA-2026), Big Soda surveillance (Coca-Cola cannot monitor a locally rendered gradient), and state-sponsored glass tilting (prevention: the glass tilts at user will). For a complete threat model, see the [Threat Model](#-threat-model) section.

### Is this a Google interview project?
Master (Rafa) said it is. So it is.

### Why did the carrier pigeon protocol use RFC 1149 instead of RFC 2549?
RFC 2549 (IP over Avian Carriers with Quality of Service) adds QoS classification, bird retransmission timers, and flock management that were deemed unnecessary for a single physical document transfer. The pseudocode documents were transported in a single flight, within visual line of sight, with no QoS guarantees required. Should multi-bird formations become necessary in future development, RFC 2549 adoption would be reconsidered.
